# Follow-up queries with novelty limits: frozen criteria / 带新颖性限制的补查：冻结标准

Date: 2026-11-07. Written before any arm was run (code for the harness and planner prompts `followup/planner-A.txt`, `followup/planner-B.txt` existed; no planner call, no follow-up retrieval, no control run). Frozen by `P6-FOLLOWUP-NOVELTY-CRITERIA.sha256` (this file + both planner prompts).
日期：2026-11-07。在运行任何实验组之前写定（harness 代码与规划器提示词 `followup/planner-A.txt`、`followup/planner-B.txt` 已存在；尚未进行任何规划调用、补查检索或对照运行）。由 `P6-FOLLOWUP-NOVELTY-CRITERIA.sha256` 冻结（本文件 + 两份规划器提示词）。

## Question / 问题
- EN: Earlier follow-ups (one round, ≤ 3 model-planned queries) added almost nothing (recall 0.818 → 0.821) because they re-found evidence the first call had already delivered. If every follow-up result must add *new* evidence (overlap gate, per-turn near-duplicate filter, MMR-style diversity, a planner that sees what was found and asks only for what is missing), do follow-ups now find genuinely new gold evidence, and is that gain more than "more bytes" buys without any model call?
- 中文：此前的补查（一轮、≤ 3 个模型规划的查询）几乎没有增益（召回 0.818 → 0.821），因为它们重新找到了第一次调用已交付的证据。如果要求每个补查结果必须带来*新*证据（重叠率门槛、逐轮近重复过滤、MMR 式多样性、让规划器看到已找到内容并只询问缺失内容），补查能否找到真正新的金标证据？该增益是否超过不调用模型、仅多给字节所能买到的？

## Design / 设计
- EN: Everything model-related lives in the eval harness (`followup/followup.mjs`, `followup/followup-score.py`); LITSAN owns no model call and gets no new request parameter. Per question: (1) first call = `litsan_context(question)` under N4200; (2) one planner call (Codex `gpt-5.6-luna`, reasoning low, same wrapper settings as `attribution-20261106/multihop`, prompt cached by hash) sees the question and the first context's passages and returns `{sufficient, missing, queries ≤ 3}`; (3) if not sufficient, each query (max 3, first 3 kept) goes through `litsan_context(query)` under the same N4200 flags; (4) an admission policy decides which returned units are appended to the first context as a `followUpEvidence` block; (5) the scored text is first-context text + appended block, so complete raw/cited, bytes and latency are measured on exactly what a Harness would receive. Appending never removes baseline content, so a policy can only gain on complete raw; the cost is bytes, one model call and extra retrieval calls.
- 中文：所有与模型相关的逻辑都在评测 harness（`followup/followup.mjs`、`followup/followup-score.py`）；LITSAN 不拥有任何模型调用，也不新增请求参数。每道题：(1) 首次调用 = N4200 下的 `litsan_context(问题)`；(2) 一次规划调用（Codex `gpt-5.6-luna`，推理 low，沿用 `attribution-20261106/multihop` 的包装设置，提示词按哈希缓存）看到问题和首次上下文的段落，返回 `{sufficient, missing, queries ≤ 3}`；(3) 若不充分，每个查询（至多 3 个，保留前 3 个）在相同 N4200 开关下走 `litsan_context(查询)`；(4) 准入策略决定哪些返回单元作为 `followUpEvidence` 块追加到首次上下文之后；(5) 评分文本 = 首次上下文文本 + 追加块，因此完整原文/引用、字节与延迟都按 Harness 实际收到的内容测量。追加从不删除基线内容，因此策略只可能提高原文完整；代价是字节、一次模型调用和额外的检索调用。
- EN: Units. From each response: raw units = passages of the entry with id `adaptive:raw-evidence` (`evidence_ref`, `text`); fact units = passages of the L2 entry with a `fact_id` (`text`, cited refs parsed from `Evidence: l1:…`). Delivered raw set R0 = raw refs of the first context; delivered fact set F0 = its fact ids. Tokens for similarity = lowercase `[a-z0-9]+` of the text, with a leading `[timestamp]` and for facts the `Atomic fact:` prefix and ` | Evidence:…` suffix removed, tokens of length 1 dropped. Jaccard = |A∩B| / |A∪B| of token sets.
- 中文：单元。每个响应中：原文单元 = id 为 `adaptive:raw-evidence` 的条目的段落（`evidence_ref`、`text`）；事实单元 = L2 条目中带 `fact_id` 的段落（`text`，引用的 ref 从 `Evidence: l1:…` 解析）。已交付原文集合 R0 = 首次上下文的原文 ref；已交付事实集合 F0 = 其 fact id。相似度分词 = 文本的小写 `[a-z0-9]+`，去掉开头的 `[时间戳]`，事实还去掉 `Atomic fact:` 前缀和 ` | Evidence:…` 后缀，丢弃长度为 1 的词。Jaccard = 词集交集 / 并集。
- EN: Admission policies (all share *exact dedupe*: a raw unit whose ref is in R0 or already admitted, or a fact unit whose id is in F0 or already admitted, is never appended; this is the merge semantics of the old behaviour). Units are considered in follow-up order, then response order. Appended bytes of a unit = UTF-8 bytes of `text` plus of its ref/id.
  - `F0` (old behaviour, no novelty limit): exact dedupe only, no cap.
  - `C2K` (cap control): exact dedupe, cap 2,000 appended bytes (units that do not fit are skipped, later smaller units may still fit). Separates "novelty" from "a cap".
  - `OV` (overlap gate): a follow-up whose raw units have overlap > 0.5 (share whose ref is in R0 or already admitted) is rejected entirely; otherwise exact dedupe; cap 2,000.
  - `JA` (per-unit near-duplicate): additionally skip a unit whose max Jaccard against all delivered and already admitted raw and fact texts is ≥ 0.6; cap 2,000.
  - `OJ`: `OV` gate plus the `JA` filter; cap 2,000.
  - `MM` (MMR across follow-ups): candidates = all units of all follow-ups after exact dedupe; greedy selection with score = 0.5·rel − 0.5·sim, rel = 1/(1+position in its follow-up's result list), sim = max Jaccard to delivered ∪ already selected; skip a candidate whose best score ≤ 0; cap 2,000.
- 中文：准入策略（均先做*精确去重*：原文单元的 ref 已在 R0 或已准入、事实单元的 id 已在 F0 或已准入，则不追加；这是旧行为的合并语义）。按补查顺序、再按响应顺序考察单元。单元追加字节 = `text` 与其 ref/id 的 UTF-8 字节数。
  - `F0`（旧行为，无新颖性限制）：仅精确去重，无上限。
  - `C2K`（上限对照）：精确去重，追加字节上限 2,000（放不下的单元跳过，之后更小的单元仍可放入）。用来区分"新颖性"与"上限"。
  - `OV`（重叠门槛）：补查的原文单元重叠率 > 0.5（ref 已在 R0 或已准入的占比）则整条补查被拒绝；否则精确去重；上限 2,000。
  - `JA`（逐单元近重复）：另外跳过与所有已交付及已准入的原文和事实文本的最大 Jaccard ≥ 0.6 的单元；上限 2,000。
  - `OJ`：`OV` 门槛加 `JA` 过滤；上限 2,000。
  - `MM`（跨补查的 MMR）：候选 = 所有补查在精确去重后的全部单元；贪心选择，得分 = 0.5·rel − 0.5·sim，rel = 1/(1+其在所属补查结果列表中的位置)，sim = 与已交付 ∪ 已选的最大 Jaccard；最佳得分 ≤ 0 的候选跳过；上限 2,000。
- EN: Planner prompts. `A` = the old progressive-disclosure prompt (sufficiency judgment and up to 3 queries, `followup/planner-A.txt`). `B` = missing-aware prompt (lists FOUND, asks only for what is missing, queries must not reuse FOUND wording and must differ from each other, `followup/planner-B.txt`). Per case the user block is `{"id","question","FOUND":{"raw_turns":[{"ref","text"}…],"facts":[{"text"}…]}}` in context order; one case per call so model calls per question are exactly 1. A malformed answer is retried once (same prompt + a JSON-validity reminder); a question whose planner fails twice counts as "no follow-up" and is reported.
- 中文：规划器提示词。`A` = 旧的渐进披露提示（充分性判断加至多 3 个查询，`followup/planner-A.txt`）。`B` = 感知缺失的提示（列出 FOUND，只询问缺失内容，查询不得复用 FOUND 的措辞且彼此不同，`followup/planner-B.txt`）。每次调用一个案例，因此每题模型调用恰为 1。格式错误的回答重试一次（同提示词 + JSON 有效性提醒）；规划器两次均失败的题按"无补查"计并报告。

## Arms / 实验组
- EN: Baseline `N4200` (flags `LITSAN_DERIVED_FACT_RETRIEVAL=semantic`, `LITSAN_DERIVED_RAW_EVIDENCE=always`, `_MAX=16`, `_ORDER=cited_first`, `_SEMANTIC_LEAD=8`, `_BYTES=4200`, `LITSAN_CONTEXT_LEAN=1`). N4200 is turn-capped, not byte-capped (560 of 649 tuning responses hold exactly 16 raw turns, mean 3.56 KB raw), so a larger `_BYTES` alone changes nothing. Byte-matched controls therefore also raise `_MAX` (the clamp was raised from 16 to 48 for this study; unset still means 8, so defaults are unchanged): rungs `R1` (MAX 24, BYTES 5200), `R2` (32, 6200), `R3` (40, 7700), `R4` (48, 9200), `R5` (48, 12200). Planner arms are `{A,B} × {F0, C2K, OV, JA, OJ, MM}` = 12 arms, named e.g. `A-OV`. No other arm, threshold or cap may be added after the first planner result is seen.
- 中文：基线 `N4200`（开关 `LITSAN_DERIVED_FACT_RETRIEVAL=semantic`、`LITSAN_DERIVED_RAW_EVIDENCE=always`、`_MAX=16`、`_ORDER=cited_first`、`_SEMANTIC_LEAD=8`、`_BYTES=4200`、`LITSAN_CONTEXT_LEAN=1`）。N4200 受轮次数而非字节限制（649 个调参响应中 560 个恰好含 16 个原始轮次，平均 3.56 KB 原文），所以单独加大 `_BYTES` 不会有任何变化。因此字节匹配对照同时提高 `_MAX`（本研究把上限从 16 提到 48；未设置时仍为 8，默认行为不变）：档位 `R1`（MAX 24、BYTES 5200）、`R2`（32、6200）、`R3`（40、7700）、`R4`（48、9200）、`R5`（48、12200）。规划器实验组为 `{A,B} × {F0, C2K, OV, JA, OJ, MM}` 共 12 组，如 `A-OV`。看到第一个规划结果之后，不得再增加任何实验组、阈值或上限。
- EN: Matched control of an arm on a question set = the smallest rung whose *mean total response bytes on that set* is ≥ the arm's mean total bytes (the control is allowed to be larger, which is conservative against the arm). If the arm exceeds R5 it has no matched control and cannot be called validated.
- 中文：某实验组在某题集上的匹配对照 = 该题集上*平均响应总字节*不小于该组平均总字节的最小档位（允许对照更大，这对该组是保守的）。若该组超过 R5，则没有匹配对照，不能判为已验证。

## Measures / 指标
- EN: Per question and per arm: complete raw (every gold turn's own first 60 normalized characters are in the delivered text; same scorer as `run.mjs`), complete raw-or-cited, raw recall, total bytes, retrieval latency (first call + follow-up `litsan_context` calls, ms), planner latency (ms, reported separately), model calls (planner arms: 1; baseline and rungs: 0), `litsan_context` calls. Paired exact McNemar (two-sided) and the 95% CI of the paired difference (Wald, as `paired-p3.py`, plus a 10,000-resample paired bootstrap), arm vs baseline and arm vs matched control; per-category net; gain per extra KB and per model call.
- 中文：每题每组：原文完整（每个金标轮次自身前 60 个规范化字符都在交付文本中；评分器与 `run.mjs` 相同）、原文或引用完整、原文召回、总字节、检索延迟（首次调用 + 补查 `litsan_context` 调用，毫秒）、规划器延迟（毫秒，单独报告）、模型调用数（规划器组 1；基线与档位 0）、`litsan_context` 调用数。配对精确 McNemar（双侧）与配对差的 95% 置信区间（Wald，同 `paired-p3.py`，另加 10,000 次重采样的配对 bootstrap），分别对基线和匹配对照；按类别的净增；每多 1 KB 与每次模型调用的增益。
- EN: **Useful evidence**: a unit is useful when it is a raw turn whose ref is a gold turn of the question and not in R0 (newly delivered gold). A follow-up is **useful** if it returns ≥ 1 useful unit before any admission policy; **clearly useless** if its raw overlap with R0 is > 0.5 and it returns no useful unit; the rest are neutral. An admitted unit is **clearly useless** if it is not gold. Report per planner prompt: share of questions that trigger follow-ups, follow-up counts by class, mean overlap, admitted units and bytes, admitted-unit precision (gold share), and bytes per newly gained gold turn. Gold labels are used only for scoring, never by a policy or the planner.
- 中文：**有用证据**：单元是其 ref 属于该题金标轮次且不在 R0 的原文轮次（新交付的金标）。补查在任何准入策略之前返回 ≥ 1 个有用单元则为**有用**；其原文与 R0 的重叠率 > 0.5 且无有用单元则为**明显无用**；其余为中性。被准入的单元若不是金标则**明显无用**。按规划器提示词报告：触发补查的题占比、各类补查数、平均重叠率、准入单元数和字节、准入单元精度（金标占比）、每新增一个金标轮次所花字节。金标仅用于评分，策略和规划器均不可使用。

## Pools / 题集
- EN: **Tuning**: `sets/p3-tune-pool.json` only (649; dev 50, holdout 57, fresh 85, signal tune 457). **Final**: `sets/followup-residual.json` (184 LoCoMo category 1/2 questions with gold turns; 74 multi-hop, 110 temporal), built before any arm by taking every category 1–4 question that appears in no set file, no `questions.json`, no dev/holdout/fresh file of `attribution-20261106` and no `used-ids.txt` entry (sha256 `5b389aaa…`). They sit in the attribution study's answer-level *dev* pool but were never retrieved or scored in this harness or tuned on in any round. The 468-question `confirm` set is *not* used (already used for P4, P5 and the answer-side session). Power is limited: with 184 questions only a net gain of about 4–5 questions reaches p ≤ 0.05.
- 中文：**调参**：仅用 `sets/p3-tune-pool.json`（649 题；dev 50、holdout 57、fresh 85、signal tune 457）。**最终检验**：`sets/followup-residual.json`（184 道有金标轮次的 LoCoMo 类别 1/2 题；多跳 74、时间 110），在运行任何实验组之前构建：取所有未出现在任何题集文件、任何 `questions.json`、`attribution-20261106` 的任何 dev/holdout/fresh 文件及 `used-ids.txt` 中的类别 1–4 题（sha256 `5b389aaa…`）。它们属于归因研究的回答层 *dev* 池，但在本 harness 中从未被检索或评分，也未在任何一轮中用于调参。468 题 `confirm` 集*不使用*（已用于 P4、P5 和回答侧会话）。检验力有限：184 题时只有净增约 4–5 题才能达到 p ≤ 0.05。

## Selection on the tuning pool / 调参池上的选择
- EN: For each of the 12 arms compute net complete-raw gain vs its matched control on the tuning pool. An arm is **eligible** if net vs matched control ≥ +5 and exact McNemar p ≤ 0.05 (gained > lost) vs that control. **Pick** = the eligible arm with the largest net vs matched control (ties: fewer mean bytes, then fewer follow-up calls). Also report every arm vs baseline, the evidence-vs-bytes frontier with the rungs, and F0 of both prompts. If no arm is eligible, there is no pick, the final set is **not run**, and the outcome is **failed** (the unused pool is kept for a better idea). Planner prompt and policy are chosen jointly from the 12 arms; nothing else is tuned.
- 中文：对 12 个组分别计算调参池上相对其匹配对照的原文完整净增。若相对匹配对照净增 ≥ +5 且相对该对照的精确 McNemar p ≤ 0.05（增 > 减），该组**合格**。**入选** = 合格组中相对匹配对照净增最大者（并列：平均字节更少者，再比补查调用更少者）。同时报告每组相对基线的结果、含各档位的证据-字节前沿，以及两种提示词的 F0。若没有合格组，则无入选，**不运行**最终集，结论为**失败**（未使用的题集留给更好的想法）。规划器提示词与策略从 12 组中联合选取；不调其他任何东西。

## Final check / 最终检验
- EN: Run once on `followup-residual`: baseline N4200, the pick, the pick's prompt with `F0` (old behaviour) and `C2K` (cap control), the pick's matched control rung (and the next smaller rung for context), no parameter changes. Verdicts for the pick:
  - **Validated**: complete raw gain vs baseline with exact McNemar p ≤ 0.01; **and** net vs matched control ≥ +4 with exact McNemar p ≤ 0.05; **and** mean bytes ≤ matched control's. Model-call cost (1 planner call per question plus ≤ 3 extra retrievals) is reported with the gain; it is not waived.
  - **Promising**: not validated but complete raw gain vs baseline has p ≤ 0.05 and net vs matched control ≥ +1.
  - **Failed**: otherwise, including any case where the gain is not larger than what the matched control buys.
- 中文：在 `followup-residual` 上只运行一次：基线 N4200、入选组、入选提示词下的 `F0`（旧行为）和 `C2K`（上限对照）、入选组的匹配对照档位（及再小一档作参考），不改参数。对入选组的判定：
  - **已验证**：相对基线的原文完整增益精确 McNemar p ≤ 0.01；**且**相对匹配对照净增 ≥ +4 且精确 McNemar p ≤ 0.05；**且**平均字节不超过匹配对照。模型调用成本（每题 1 次规划调用加 ≤ 3 次额外检索）与增益一并报告，不予豁免。
  - **有希望**：未达已验证，但相对基线的原文完整增益 p ≤ 0.05，且相对匹配对照净增 ≥ +1。
  - **失败**：其他情形，包括增益不大于匹配对照所能买到的任何情况。
- EN: A tuning-only positive is at most "promising, tuning only"; past rounds show tuning gains often fail on fresh sets. Answer accuracy is not measured here.
- 中文：仅在调参池上为正，最多算"有希望，仅调参"；以往各轮显示调参增益常常无法迁移到新题集。此处不测回答准确率。
